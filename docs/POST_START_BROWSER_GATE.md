# Post-start browser regression boundary

A real authenticated browser session exposed a delayed hang shortly after `Start New Game`. The failure reproduced in both `legacy` and `parity`, which ruled out Cloudflare Access, OTP, ULS entitlement handling, and Gateway parity as the cause. Isolation showed that ordinary gameplay remained responsive when the Adaptive Tutor UI/core path was withheld.

The production boundary is now explicit: ordinary Cancellation Hearts startup may load the Tutor capability and pre-register Tutor extension sources, but it must not construct the real Adaptive Coach core. The core is constructed exactly once only when the user explicitly enters Tutor mode. Tutor extensions are installed at that same initialization boundary, after the core exists, and repeated Tutor starts reuse the existing core.

The real-browser gate therefore protects both sides of the boundary. For `legacy` and `parity`, it starts a normal eight-player game, waits through the former crash window, verifies the page remains responsive, and asserts Tutor-core construction count remains zero. It separately enters Tutor through the real `gameMode`/`Start Tutor` control, verifies one real core construction, verifies the opening diagnostic is visible, and verifies a repeated Tutor start does not construct another core. In parity mode the local harness returns an explicit authorization denial for Gateway calls so fail-closed learning-service behavior is also proven not to crash gameplay.
